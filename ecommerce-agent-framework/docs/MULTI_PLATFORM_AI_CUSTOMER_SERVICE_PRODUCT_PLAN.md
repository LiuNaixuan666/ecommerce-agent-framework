# 多平台本地 AI 客服产品目标与实施计划

更新时间：2026-06-18

## 1. 背景与新目标

当前项目已经从“单一聊天/RAG 系统”推进到了“本地 Local Agent + 浏览器页面自动化 + 拼多多 dry-run 验证”的阶段。下一步不应该只继续堆技术能力，而要把产品形态收束成一个商家真正能理解和使用的工作台。

新的产品目标是：

> 做一个本地运行的多平台 AI 客服中台，让商家可以用一套知识库、一套回复策略、一套风控规则，同时接入多个电商平台。第一阶段主攻拼多多，后续扩展闲鱼、淘宝/千牛、京东、抖店等平台。

这个系统初期不依赖平台官方 API。平台聊天窗口、商品后台、订单上下文等信息优先通过浏览器页面自动化读取。商家登录各平台后，系统在本地浏览器环境中实时读取买家消息、商品信息和上下文，调用本地后端生成回复，并根据风险策略决定自动发送还是转人工。

## 2. 参考产品观察

根据参考截图，竞品的核心流程大致是：

1. 配置店铺信息。
2. 选择 AI 回复策略。
3. 登录各个平台工作台。
4. 导入商品信息并生成商品知识。
5. 设置通用规则、政策、问答模板。
6. 选择接待模式。
7. 运行 AI 客服。
8. 基于历史聊天记录优化回复质量。

截图里可以借鉴的模块包括：

- 多平台入口：抖店、京东、拼多多、千牛、闲鱼、微信小店、小红书、快手等平台以图标卡片呈现。
- 知识库配置：区分商品信息管理和通用信息管理。
- 商品导入：支持从平台抓取商品，支持全部获取或部分获取。
- 商品学习：抓取商品标题、类目、价格、规格、描述等信息后，生成常见问答。
- 通用信息：配置发货时效、物流、退换货、售后规则等跨商品政策。
- AI 回复策略：支持全托管、人机协作、智能转接三种模式。
- 转人工触发项：关键词、图片消息、通用工单、售后风险、超出知识库等。
- 回复配置：回复风格、严格按问答组回复、分段回复、新客自动问候、敏感词过滤。
- 运行工作台：左侧显示平台账号和运行状态，中间嵌入对应平台客服页面。
- 优化 AI 回复：按平台、商品、时间范围分析历史聊天记录，发现低质量回复后人工修正，再沉淀回知识库。

这些能力不是都要一次做完，但它们给了我们清晰的产品闭环。

## 3. 我们不照搬，应该升级的地方

参考产品更像“RPA 套壳 + 知识库配置工具”。我们的优势可以放在三个方向：

1. 可解释的自动发送边界

   我们已经有 `auto_send_allowed`、`risk_level`、`action`、`auto_send_blockers` 等结构化决策字段。后续 UI 不只显示“AI 回复了什么”，还要显示“为什么能自动发送”或“为什么必须转人工”。

2. 可插拔平台适配器

   不为每个平台硬写一套流程，而是统一成：

   - 登录状态检测
   - 买家消息读取
   - 商品上下文读取
   - 订单上下文读取
   - 回复框回填
   - 发送结果校验
   - 异常和重试策略

   拼多多是第一个 adapter，闲鱼、千牛等后续复用同一套抽象。

3. 商品知识和文档 RAG 绑定

   竞品看起来更多是把商品信息转成问答卡片。我们需要更强的绑定关系：

   - 商品结构化数据来自平台抓取、Excel/CSV、商家数据库。
   - 商品说明文档、FAQ、政策文档通过 RAG 入库。
   - 每个 chunk 必须带上 `platform`、`product_id`、`sku_id`、`doc_type`、`source` 等 metadata。
   - 客服回复时先根据当前会话商品上下文检索对应商品知识，再回退到店铺通用知识。

## 4. 产品定位

产品名称暂定：本地多平台 AI 客服中台。

目标用户：

- 同时经营多个电商平台的中小商家。
- 不想在每个平台单独购买、配置、训练 AI 客服的商家。
- 没有能力申请官方开放平台 API，但可以保持电脑在线运行客服工作台的商家。

核心价值：

- 多平台统一接待。
- 一套商品知识和政策规则复用到多个平台。
- 本地运行，不需要把店铺账号交给第三方云服务。
- 低风险问题自动回复，高风险问题自动转人工。
- 通过历史聊天不断优化知识库和话术。

## 5. 总体产品结构

建议前端重构为一个真正的工作台，而不是单一聊天页。

主要导航：

1. 综合工作台
2. 平台接入
3. 知识库配置
4. AI 回复策略
5. 运行日志
6. 数据分析
7. 系统设置

### 5.1 综合工作台

用途：商家每天打开系统后的主界面。

页面内容：

- 平台卡片：拼多多、闲鱼、淘宝/千牛、京东、抖店等。
- 每个平台显示：
  - 登录状态
  - Local Agent 运行状态
  - AI 接待模式
  - 今日接待人数
  - 自动回复数
  - 转人工数
  - 最近异常
- 点击平台卡片进入对应平台工作台。
- 支持启动/暂停平台 Agent。
- 支持进入 dry-run 模式观察，不真实发送。

第一版只做拼多多可用，其他平台显示“待接入”。

### 5.2 平台接入

用途：管理不同平台的接入方式和浏览器自动化配置。

平台接入页需要包含：

- 平台列表。
- 平台登录入口。
- 浏览器 profile 管理。
- 当前选择器配置状态。
- 连接测试。
- 最新 heartbeat。
- 最近一次读取到的买家消息。
- 最近一次发送结果。

拼多多第一阶段能力：

- 打开拼多多客服页。
- 检测是否已登录。
- 检测是否已选中会话。
- 读取最新一条买家消息。
- 读取当前商品卡片信息。
- dry-run 生成回复。
- 真实发送必须显式打开安全开关。

### 5.3 知识库配置

知识库分为四层：

1. 商品结构化知识

   来自平台商品后台抓取、Excel/CSV 导入、商家数据库连接。

2. 商品文档知识

   商品说明书、尺码表、材质说明、适用人群、安装说明等。

3. 店铺通用知识

   发货时效、运费规则、退货政策、换货政策、售后流程、客服口吻。

4. 问答模板知识

   商家确认过的高频问答和标准话术。

商品知识必须绑定商品：

```text
merchant_id
platform
shop_id
product_id
sku_id
doc_type
source_type
source_url / file_id
updated_at
```

检索优先级：

1. 当前会话商品的专属知识。
2. 当前平台的商品知识。
3. 店铺通用政策。
4. 通用问答模板。
5. 无证据时转人工或给出低承诺回复。

### 5.4 AI 回复策略

建议设计三种接待模式：

#### 模式 A：AI 全托管

适用场景：

- 低风险售前咨询。
- 明确商品信息。
- 明确店铺政策。
- 问候、价格、库存、发货时间、尺码建议等常规问题。

规则：

- 低风险且证据充分时自动发送。
- 中高风险直接转人工。
- 无证据不编造。

#### 模式 B：人机协作

适用场景：

- 商家刚开始试用。
- 平台页面或选择器还不稳定。
- 希望 AI 先生成推荐回复，人工审核后发送。

规则：

- 默认不自动发送。
- 低风险可配置为自动发送。
- 所有中高风险进入人工待处理。

#### 模式 C：智能转接

适用场景：

- 多客服团队。
- 需要把售后、投诉、退款、敏感词问题转给指定人工。

规则：

- AI 处理常规问题。
- 命中转接规则时不生成强答复，只生成摘要和处理建议。
- 可配置转接原因和目标账号。

### 5.5 运行日志

运行日志是后续排查错发、漏发、慢回复的关键。

每条消息应记录：

- 平台
- 店铺
- 会话 ID
- 买家消息
- 商品上下文
- 检索到的知识来源
- 生成回复
- 风险等级
- 是否允许自动发送
- 阻断原因
- 发送状态
- 失败原因
- 重试次数
- 处理耗时

### 5.6 数据分析与知识优化

参考产品里“优化 AI 回复”很重要，我们也应该做，而且要做得更可控。

第一版目标：

- 按平台、商品、时间范围查看历史接待记录。
- 标记以下问题：
  - AI 未命中知识。
  - AI 回复被转人工。
  - 用户重复追问。
  - 发送失败。
  - 人工改写过 AI 回复。
- 商家可以把人工确认后的答案加入：
  - 商品 FAQ
  - 店铺通用 FAQ
  - 风险关键词
  - 禁止自动发送规则

## 6. 与当前系统的差距

当前已经具备：

- FastAPI 后端。
- 前端基础页面。
- 文档上传与 RAG。
- 结构化客服回复。
- 自动发送边界字段。
- 风险策略。
- Local Agent 骨架。
- Mock 客服闭环。
- 浏览器页面 Adapter 原型。
- 拼多多真实页面 dry-run。
- latest-only 安全策略。
- `--allow-real-send` 显式真实发送开关。

还缺：

- 多平台首页和平台卡片。
- 平台接入管理 UI。
- 拼多多工作台状态 UI。
- 商品信息导入页面。
- 商品知识 metadata 绑定。
- AI 接待模式配置 UI。
- 转人工规则配置 UI。
- 历史对话优化 UI。
- 本地商家数据库/商品库。
- 多平台 adapter 配置管理。
- 运行日志可视化。

## 7. 目标技术架构

建议保持当前本地优先架构：

```text
前端工作台
  -> FastAPI 后端
    -> Chat Workflow
    -> Knowledge / RAG
    -> Risk Policy
    -> Product Store
    -> Conversation Store
    -> Local Agent Status
  -> Local Agent 进程
    -> Platform Adapter
      -> Browser Watcher
      -> Page Context Extractor
      -> Reply Executor
      -> Send Verifier
```

核心原则：

- 平台差异只放在 adapter 和 selector profile 中。
- 回复生成、风险策略、知识检索尽量平台无关。
- 真实发送必须有可追踪日志。
- 默认 dry-run，真实发送需要显式配置。
- 同一会话串行处理，避免多条消息乱序回复。

## 8. 分阶段实施计划

### 阶段 5：多平台控制台产品骨架

目标：把系统首页从普通聊天页升级为多平台客服中台。

状态：✅ 已完成（2026-06-19）

完成后端：
- 新增 `GET /api/platform/list` — 平台注册表 + 实时 Agent 状态合并。
- 新增 `GET /api/platform/{code}/status` — 平台详情（Agent 列表 + 发送记录）。
- 5 个平台已注册（拼多多 active，其余 coming_soon）。

完成前端：
- 深色侧边栏导航（含折叠），7 个页面入口。
- 综合工作台首页：统计概览 + 平台卡片（已接入/待接入分组）。
- 拼多多工作台详情页：Agent 列表 + 心跳 + 发送记录表格。
- 平台接入、AI 回复策略、运行日志页面骨架。
- Mock 工作台和知识库聊天保留在开发工具分组中。

### 阶段 6：拼多多平台工作台 MVP

目标：把已有拼多多 dry-run 能力产品化。

状态：✅ 已完成（2026-06-19）

完成内容：
- 后端 Heartbeat 模型增加 `latest_buyer_message`、`selector_profile`、`current_page_url` 监控字段。
- 新增 `POST /api/local-agent/seed-demo` 开发用演示数据注入端点。
- 前端新增「会话监控」面板，展示买家消息、商品上下文、AI 决策、监控配置。
- 前端新增「安全控制」区域，Dry-Run / 允许真实发送切换开关。
- 前端自动轮询刷新（每 5 秒）。
- 验收通过：商家在页面上可以看到”系统读到了什么、准备回什么、为什么能发或不能发”，默认 Dry-Run。

### 阶段 7：商品信息导入与商品知识绑定

目标：解决“当前商品对应哪个知识库”的核心问题。

要做：

- 建立本地商品表。
- 支持 CSV/Excel 导入商品。
- 支持拼多多页面抓取商品基本信息。
- 支持给商品上传文档。
- 文档 chunk 写入 metadata。
- RAG 查询时根据当前商品上下文过滤或加权。

商品字段第一版：

```text
id
platform
shop_id
platform_product_id
sku_id
title
category
price
stock
shipping_rule
description
attributes_json
source_type
source_url
updated_at
```

验收：

- 上传一个商品说明文档后，只在对应商品咨询里优先命中。
- 店铺通用政策仍可跨商品生效。
- 不同商品的文档不会互相污染。

### 阶段 8：AI 回复策略配置化

目标：把当前代码中的风险判断变成商家可配置策略。

要做：

- UI 中选择 AI 全托管、人机协作、智能转接。
- 配置转人工触发项：
  - 退款/退货
  - 投诉
  - 差评
  - 赔偿
  - 敏感词
  - 图片消息
  - 订单/售后
  - 超出知识库
- 配置回复风格。
- 配置是否允许低风险自动发送。
- 配置新客问候。

验收：

- 模式变化会影响后端 `auto_send_allowed`。
- 高风险问题稳定转人工。
- 低风险问题在全托管模式下可自动发送。

### 阶段 9：历史对话学习与回复优化

目标：让系统越用越好，而不是每次靠重新上传文档。

要做：

- 保存对话历史和 AI 决策。
- 读取平台历史聊天记录。
- 标记转人工问题。
- 商家确认标准答案。
- 一键加入商品 FAQ 或通用 FAQ。
- 支持按商品查看历史问答。

验收：

- 一条 AI 不会回答的问题，人工处理后可以沉淀为模板。
- 后续同类问题能直接命中。

### 阶段 10：闲鱼等第二平台扩展

目标：验证 adapter 抽象是否真的可迁移。

要做：

- 新增闲鱼平台卡片。
- 建立闲鱼 selector profile。
- 实现闲鱼消息读取、商品上下文读取、回复回填。
- 复用同一套后端 workflow 和风险策略。

验收：

- 不改核心 Chat Workflow，只新增平台 adapter/profile 即可接入第二个平台。

## 9. 安全边界

真实平台自动回复有实际经营风险，所以必须保留以下边界：

- 默认 dry-run。
- 真实发送必须显式开启。
- 只处理最新一条买家消息。
- 同一会话串行处理。
- 中高风险不自动发送。
- 无证据不编造。
- 发送后必须校验。
- 失败必须回写。
- 每次自动发送必须留日志。

建议 UI 中把自动发送开关做成平台级配置，而不是隐藏在命令行里。命令行仍保留 `--allow-real-send` 作为底层保险。

## 10. 主要风险

1. 平台 DOM 变化

   需要 selector profile 可编辑、可测试、可回滚。

2. 登录态不稳定

   需要专用浏览器 profile 和登录状态检测。

3. 多会话并发

   初期只处理当前选中会话。后续再做会话列表扫描和队列。

4. 错误商品绑定

   商品 ID、SKU、标题、商品卡片 URL 必须作为上下文共同参与匹配。

5. 自动发送风险

   必须坚持结构化决策和风险阻断，不允许仅凭模型一句话直接发。

6. 本地电脑必须在线

   这是无 API 路线的天然限制，需要在产品说明中明确。

## 11. 下一步建议

当前不要直接追求更多真实平台。建议下一步进入：

> 阶段 5：多平台控制台产品骨架。

具体先做：

1. 前端首页改成多平台工作台。
2. 拼多多平台卡片接入已有 Local Agent 状态。
3. 做一个拼多多平台详情页，展示 dry-run 读取结果和 AI 决策。
4. 暂不真实发送，继续保持安全验证。

这样做的好处是：我们不会陷在“继续命令行测试拼多多选择器”的技术细节里，而是让项目开始有完整产品样子，同时又复用已经跑通的后端和 Local Agent 能力。

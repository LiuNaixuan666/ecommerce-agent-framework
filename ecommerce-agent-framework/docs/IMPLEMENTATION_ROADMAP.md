# 本地 RPA 电商智能客服实施路线图

> 当前最新主线以 `docs/CURRENT_GOAL_AND_PROGRESS.md` 和 `docs/SELF_BUILT_LOCAL_AGENT_PLAN.md` 为准。
> 本路线图保留原有阶段资料，同时新增自研 Local Agent 路线，后续实现按新路线推进。

## 1. 实施原则

本项目后续开发遵循以下原则：

1. 先验证闭环，再追求自动化。
2. 先做本地稳定，再考虑云端和平台 API。
3. 默认支持低风险问题自动发送，高风险和低置信度问题转人工。
4. 先接商家可控数据，再依赖网页抓取信息。
5. 所有 AI 回复都需要可追溯来源和风险等级。
6. 自研 Local Agent 是后续核心执行层，影刀等第三方 RPA 只作为可选验证工具。
7. 先用 Mock 客服页面验证完整闭环，再扩展真实平台适配器。

## 1.1 当前最新阶段路线

### 阶段 1 收尾：Local Agent 闭环接口

目标：

- 补齐 Local Agent 与后端闭环所需接口。

任务：

- 新增 `POST /api/chat/rpa/send-result`。
- 新增 `POST /api/local-agent/heartbeat`。
- 更新 `docs/RPA_INTERFACE_SCHEMA.md`。
- 更新执行跟踪。

验收：

- 后端能记录发送成功、失败、转人工、重复跳过、过期跳过。
- 后端能记录 Local Agent 在线状态和最近监听状态。
- 不影响现有 `POST /api/chat/rpa/message`。

### 阶段 2：自研 Local Agent 骨架与 Mock 客服闭环

目标：

- 不依赖影刀，跑通自研 Local Agent 的最小闭环。

任务：

- 新建 `app/local_agent`。
- 实现 `BasePlatformAdapter`。
- 实现 `MockShopAdapter`。
- 做最小 Mock 客服页面。
- 实现消息去重和会话串行处理。
- Agent 调用 `/api/chat/rpa/message`。
- `auto_send_allowed=true` 时自动回填发送。
- `auto_send_allowed=false` 时标记转人工。
- Agent 调用 `/api/chat/rpa/send-result` 回写结果。

验收：

- Mock 页面出现新买家消息后，Agent 能自动处理。
- 低风险问题能自动回填发送。
- 高风险问题不会自动发送。
- 发送结果能在后端记录。

### 阶段 3：真实平台适配雏形

目标：

- 用一个真实网页客服环境验证平台适配器模式可行。

任务：

- 实现 `GenericWebChatAdapter` 或 `PddWebAdapter` 雏形。
- 读取真实页面最新买家消息。
- 读取商品上下文。
- 回填回复文本。
- 发送前做当前会话、消息过期、重复回复二次校验。

验收：

- 至少一个真实平台页面能完成有限验证。
- 真实平台失败不影响 Mock 演示闭环。

## 2. 阶段划分

### 阶段 0：现有系统稳定化

目标：让当前本地 demo 可以稳定运行、上传、问答。

任务：

- 修复前端输入消息后跳回主页的问题。
- 修复前端中文乱码问题。
- 确认后端启动流程。
- 确认 `/health`、`/api/chat/health`、`/api/knowledge/health` 正常。
- 重新测试 TXT、Markdown、PDF、DOCX 上传。
- 记录上传文件数、任务状态、chunk 数、Chroma 数据目录。
- 测试 10 个客服问题，观察过度澄清和胡编情况。

验收标准：

- 本地后端和前端能稳定启动。
- 上传 2 个测试文档后能完成入库。
- 文档内明确问题能正确回答并给出来源。
- 模糊问题会澄清。
- 文档没有答案的问题不会编造。

### 阶段 1：产品文档与接口定稿

目标：明确产品边界和后续开发结构。

任务：

- 完成 PRD。
- 完成架构设计。
- 完成路线图。
- 定义 RPA 标准输入输出。
- 定义结构化客服回复 schema。
- 定义知识库 metadata schema。
- 定义商家数据库标准商品模型。

验收标准：

- 文档可解释系统为什么不优先走平台 API。
- 文档可指导后续开发。
- RPA、数据库、知识库、回复输出的字段定义清晰。

### 阶段 2：结构化客服回复

目标：让系统从“聊天机器人”变成“客服辅助工具”。

任务：

- 修改后端 chat 响应结构。
- 增加推荐回复字段。
- 增加风险等级。
- 增加是否转人工。
- 增加缺失信息。
- 增加引用来源。
- 增加置信度。
- 前端展示风险等级、来源、自动发送状态和转人工提示。

建议响应结构：

```json
{
  "recommended_reply": "...",
  "risk_level": "low",
  "auto_send_allowed": true,
  "requires_human_review": false,
  "handoff_reason": null,
  "missing_info": [],
  "sources": [],
  "confidence": 0.82
}
```

验收标准：

- 普通商品咨询返回 low 风险，并允许自动发送。
- 退款纠纷、投诉、差评威胁返回 high 风险并要求转人工。
- 缺少订单号或商品信息时返回 missing_info。
- 前端不只显示一段文本，而是显示客服决策信息。

### 阶段 3：本地商家数据库模拟

目标：验证商家数据库可插拔和可迁移。

任务：

- 新建三个模拟商家数据库：
  - 图书商家
  - 服装商家
  - 美妆商家
- 每个数据库使用不同字段名。
- 设计标准商品模型。
- 实现字段映射配置。
- 实现本地商品查询 adapter。
- 支持按 product_id、sku、标题搜索商品。
- 支持查询价格、库存、上下架状态。

模拟数据库建议：

```text
data/demo_merchants/bookstore.db
data/demo_merchants/clothing_store.db
data/demo_merchants/beauty_store.db
```

验收标准：

- 三个数据库结构可以不同。
- 系统通过字段映射统一查询。
- 同一个 Agent 流程可以切换不同商家数据源。
- 库存和价格优先来自数据库，而不是页面抓取。

### 阶段 4：数据源配置页面

目标：让商家可以可视化接入自己的数据库。

任务：

- 新增数据源配置页面。
- 支持选择数据源类型。
- 支持填写连接信息。
- 支持测试连接。
- 支持选择商品表。
- 支持字段映射。
- 支持预览同步后的标准商品数据。
- 支持保存配置。

验收标准：

- 不改代码也能新增一个 SQLite 或 CSV 数据源。
- 商家可以看到字段映射后的商品预览。
- 连接失败时有明确错误提示。

### 阶段 5：商品知识库绑定

目标：解决 RAG 知识串商品的问题。

任务：

- 上传文档时增加适用范围选择。
- 支持全店通用文档。
- 支持平台特定文档。
- 支持商品特定文档。
- 支持 SKU 特定文档。
- chunk 入库时写入 product_id、sku、platform、doc_type。
- 检索时优先检索当前商品绑定知识。
- 多商品文档增加自动识别和人工确认机制。

验收标准：

- 问商品 A 时不会优先使用商品 B 的说明。
- 平台政策优先于店铺通用政策。
- 商品级文档能被准确引用。
- 多商品文档无法确认归属时不会作为强依据。

### 阶段 6：RPA 标准接口

目标：让影刀 RPA 可以接入本地后端。

任务：

- 新增 `/api/rpa/inbound-message`。
- 新增 `/api/rpa/recommend-reply`。
- 新增 `/api/rpa/confirm-sent`。
- 保存 RPA 事件日志。
- 给出影刀调用示例。
- 支持 RPA 传入平台、会话、商品、订单上下文。
- 支持低风险回复自动发送后的状态回写。
- 支持高风险或低置信度问题转人工。

验收标准：

- 使用 HTTP 请求可以模拟 RPA 提交买家消息。
- 后端返回结构化推荐回复。
- RPA 可以拿到推荐回复并自动回填发送。
- 自动发送后可以调用 confirm 接口记录结果。
- 禁止自动发送的问题会返回 handoff_required。

### 阶段 7：客服工作台

目标：前端从聊天 demo 演进为日常客服工具。

任务：

- 左侧展示会话列表。
- 中间展示买家消息和推荐回复。
- 右侧展示商品信息、库存、政策命中、引用来源。
- 增加一键复制。
- 增加标记已发送。
- 增加转人工标记。
- 增加“加入问答模板”入口。
- 增加自动发送记录和失败原因。

验收标准：

- 客服可以在一个页面完成看消息、看商品、看推荐回复、复制回复。
- 高风险回复有醒目提示。
- 引用来源可以查看。

### 阶段 8：问答模板沉淀

目标：让系统越用越懂商家。

任务：

- 保存 AI 不会回答的问题。
- 保存人工最终回复。
- 后台展示待沉淀问题。
- 商家确认后加入问答模板。
- 支持编辑适用平台、商品、SKU。
- 问答模板在后续回答中高优先级命中。

验收标准：

- 人工回复可以被沉淀成模板。
- 相似问题后续能优先命中模板。
- 模板可以限定适用商品和平台。

### 阶段 9：上下文记忆与压缩

目标：支持连续对话，不让长上下文拖垮回答质量。

任务：

- 保存会话消息。
- 最近几轮消息进入 Agent 上下文。
- 超过阈值自动生成摘要。
- 后续回答使用摘要加最近消息。
- 支持按商品、买家、会话检索历史。

建议阈值：

- 最近 6 轮原文保留
- 超过 12 轮生成或更新摘要
- 每次回答最多取 1 条摘要 + 最近 6 轮

验收标准：

- “这本呢”“刚才那个”这类问题能结合上下文回答。
- 长对话后回答不会明显跑题。
- 摘要可以在后台查看。

### 阶段 10：外部搜索

目标：在商家知识不足时补充公开资料，但避免编造。

任务：

- 抽象 ExternalSearchProvider。
- 支持配置是否启用外部搜索。
- 搜索结果必须带来源。
- 高风险问题禁止自动使用外部搜索直接承诺。
- 前端展示外部来源。

验收标准：

- 图书简介缺失时可根据公开来源回答。
- 回答中能显示来源。
- 没有可靠来源时明确说明不确定。

## 4. 风险与注意事项

### 4.1 RPA 稳定性风险

平台网页结构变化可能导致 RPA 失效。

缓解方式：

- RPA 只负责消息读取和回复回填。
- 核心业务逻辑放在本地后端。
- 每个平台维护独立 RPA 模板。

### 4.2 AI 编造风险

客服场景中错误承诺会带来售后风险。

缓解方式：

- 优先使用商家数据库和知识库。
- 所有回复返回来源。
- 高风险问题强制转人工。
- 无来源问题降低置信度。

### 4.3 商品知识串用风险

RAG 可能把商品 A 的信息用到商品 B。

缓解方式：

- chunk metadata 绑定 product_id 和 sku。
- 当前商品上下文优先检索。
- 多商品文档需要归属确认。

### 4.4 商家数据库差异风险

不同商家数据库字段不统一。

缓解方式：

- 使用字段映射。
- 建标准商品模型。
- 先同步到 normalized_products，再给 Agent 使用。

### 4.5 自动发送风险

自动发送可能产生不可控售后问题，尤其是赔偿、退款、投诉、平台规则相关问题。

缓解方式：

- MVP 默认允许低风险、高置信度问题自动发送。
- 中高风险问题强制转人工。
- 每条自动发送必须记录来源、置信度、风险等级和发送结果。

### 4.6 多平台并发风险

多个平台、多个买家同时咨询时，可能出现上下文串线、回复错会话、回复过期消息等问题。

缓解方式：

- 每条消息必须带 platform、shop_id、session_id。
- 同一 session_id 内串行处理。
- 不同 session_id 并行处理。
- 自动发送前检查会话是否有更新消息。
- RPA 回写发送结果时必须携带原始 message_id。

## 5. 阶段性里程碑

### M1：稳定本地知识库问答

完成后系统可以稳定上传文档并回答文档内问题。

### M2：客服结构化回复

完成后系统可以输出推荐回复、风险等级、来源和转人工建议。

### M3：商家数据库接入

完成后系统可以从模拟商家数据库读取商品、价格、库存。

### M4：RPA 自动回复闭环

完成后影刀 RPA 可以提交消息、获取回复、自动回填并发送低风险回复，高风险问题转人工。

### M5：客服工作台

完成后商家可以在前端完成日常客服辅助流程。

### M6：问答模板沉淀和上下文压缩

完成后系统可以从人工回复中学习，并支持更稳定的连续对话。

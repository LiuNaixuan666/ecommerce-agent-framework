Interim Report

An Intent-Driven Agentic RAG Framework for Scalable E-Commerce Customer Service: A Case Study on the Book Category

Abstract
随着电子商务的快速扩张，商家在客户服务领域面临着巨大的压力。尽管大语言模型（LLM）具备出色的对话能力，但其工业化应用仍受限于幻觉现象、缺乏领域知识支撑以及跨品类扩展性差等问题。本研究提出了一种**意图驱动的智能体（Intent-Driven Agent）电商 RAG 客服框架**，通过模块化设计与可控的工作流，解决这三个核心问题。

**三个核心创新点**：
(1) **语义意图驱动检索（Semantic Intent-Driven Retrieval）**：不同于单体向量库，系统根据用户意图动态选择检索源——产品咨询检索结构化 CSV，政策咨询检索非结构化 PDF/Word。这消除了传统 RAG 中的"语义干扰"问题。
(2) **多租户物理隔离（Multi-Tenant Isolation）**：每个商家的知识独立存储于 ChromaDB 中，保证了数据安全性和商家间的信息隔离。
(3) **不确定性守门员与澄清流程（Uncertainty Gatekeeper & Clarification Flow）**：通过检索置信度和查询歧义度的综合判定，系统主动触发澄清而非生成幻觉。

系统基于 Python FastAPI、LangChain 和 ChromaDB 开发。本论文以图书品类为验证案例，目前已完成知识摄取与向量化基础设施（100% 就绪），正在开发意图解析与不确定性检测模块（预期 3-4 月完成）。后续阶段将通过对比实验（Agent-RAG vs Vanilla RAG vs Pure LLM）验证框架有效性。

**关键成果**：(1) 通用多格式文档解析器；(2) 端到端的商家隔离向量库系统；(3) 模块化 Agent 工作流架构。

Keywords: Intent-Driven Retrieval; Multi-Tenant RAG; Semantic Intent Parsing; Uncertainty Detection; Agentic RAG; E-commerce Customer Service; Scalability.

1.Introduction 
1.1Background 
在数字支付与物流创新的推动下，电子商务已从根本上重塑了全球零售版图。2024年，中国网上零售额达15.5225万亿元人民币，占社会消费品零售总额的26.8%，彰显了数字市场的巨大规模。在此环境下，客户服务成为企业成功的核心：研究显示，89%的消费者倾向于从提供卓越服务的公司再次购买。
然而，传统人工客服正面临严峻挑战。人力成本的持续上升与高峰时段服务质量的不稳定，限制了企业的响应速度。相比之下，AI系统具备24/7全天候运行能力，能够消除人工服务的时间限制，确保用户随时获得即时反馈。研究表明，引入智能客服系统可显著提升客户体验，并帮助企业降低约20%的运营成本。尽管优势明显，但现有AI聊天机器人多依赖僵化的模板或窄域知识库，缺乏多商家、多品类环境所需的灵活性。这一局限性暴露了现有方案在系统可复用性上的短板。因此，开发一个可复用的、基于智能体（Agent）的任务流框架显得尤为迫切。该框架不仅需要强大的知识支撑，更需具备工作流级别的精细化控制。
本研究的核心目标是构建一个高度可扩展的智能体框架。其创新之处在于提出了一种双轨索引机制（Dual-track Indexing），通过区分处理不同性质的商户数据：
结构化产品数据：将多样化的产品信息标准化为CSV文件，实施行级索引（Row-level Indexing），以确保极高的语义密度并消除信息交叉干扰。
非结构化政策文档：对PDF、Word等叙述性文件（如退换货政策、正版保障）进行段落级索引，以保留上下文逻辑。本框架通过一个五阶段标准化工作流（意图解析、自适应检索、不确定性检测、知识注入生成、响应后处理）实现决策逻辑。
其数学表达可抽象为：Response = f(Query, K_{merchant}, S_{agent})
其中，K_{merchant}代表商家特定的知识库，S_{agent}代表定义的智能体策略（意图识别与澄清机制等）。本研究选择图书品类作为首个验证案例，其逻辑在于：图书领域兼具极高的元数据结构化程度（如ISBN、作者、类别）与极其复杂的非结构化咨询需求（从具体内容检索到抽象的推荐请求，再到多样的平台政策咨询）。这种异构数据的共存使图书领域成为测试框架健壮性的理想平台。通过简单的领域知识库替换与参数微调，该架构可无缝扩展至电子产品或服装等其他领域，从而弥合通用AI模型与特定工业应用之间的鸿沟。

1.开发一个高度自动化、模块化的 Agent 客服框架，确保商家数据的物理隔离。
2.探究意图驱动的知识路由在减少信息检索语义干扰方面的有效性。

1.3 System Architecture & Module Mapping

【新增】**System Overview**: The framework adopts a modular, layered architecture with clear responsibility separation:

- **Orchestration Layer** (`app/agent/workflow.py`) [To be implemented by Mar]: Manages the complete request lifecycle (Intent Parse → Adaptive Retrieval → Uncertainty Check → Generation).
- **Intent Layer** (`app/agent/`): Semantic intent parsing. `intent_parser.py` classifies queries into: PRODUCT_INQUIRY, POLICY_INQUIRY, ORDER_SERVICE, CHITCHAT, OTHERS.
- **Knowledge Layer** (`app/knowledge/`): Document handling. `document_parser.py` recursively parses CSV/PDF/Word; `ingestion.py` manages data ingestion pipeline.
- **Retrieval Layer** (`app/rag/`): Vector operations. `vector_store.py` manages merchant-isolated ChromaDB collections; `retriever.py` performs semantic search.
- **Evaluation Layer** (`experiments/`) [新增]: Benchmark and comparison scripts. Compares LLM-only vs Vanilla RAG vs Agent-RAG performance.

**Intent-Knowledge Mapping**: System routes queries based on intent:
- PRODUCT_INQUIRY → search `products/` (CSV)
- POLICY_INQUIRY → search `raw_docs/` (PDF/Word)
- Other intents → fallback to clarification or hybrid search

1.4 Key Coding Conventions & Academic Terminology

【新增】**Unified Variable Naming** (for paper consistency):

- `intent_confidence`: Float (0.0-1.0) from intent classifier
- `retrieval_score`: Distance/similarity from ChromaDB
- `uncertainty_threshold`: Preset threshold T for triggering clarification
- `merchant_id`: Ensures data isolation across multi-tenant stores

**Core Logic Patterns**:

- **Intent-Driven Retrieval**: `if intent == PRODUCT` → retrieve from CSV; `else if intent == POLICY` → retrieve from PDF
- **Uncertainty Detection**: `if retrieval_score < T or query_ambiguity > ambiguity_T` → trigger clarification; `else` → allow generation
- **Grounded Generation**: Core Prompt constraint: "Only answer based on retrieved information. If not found, answer 'I don't know'. Strictly prohibit hallucination."

1.5 Data Handling Conventions

【新增】**CSV Product Data Structure**:

All product CSVs (`products/*.csv`) must contain these fields:
- `id`: Unique product identifier
- `title`: Product name
- `author`: Author (for books)
- `category`: Product category
- `price`: Unit price
- `stock`: Quantity available
- `description`: Semantic description for LLM

Example: `id=1, title=\"三体\", author=\"刘慈欣\", category=\"科幻\", price=39.9, stock=15, description=\"中国科幻里程碑作品\"`

**Recursive Reading Protocol**:

- `DocumentParser.load_merchant_data()` must use `os.walk()` to recursively traverse `raw_docs/` and `products/`
- All files in these directories (except `.pyc`, `.tmp`) should be parsed
- Parse errors are logged but don't interrupt the pipeline

**Merchant Isolation Rules**:

- Vector DB collection naming: `{merchant_id}` (e.g., `merchant_a`)
- Persist path: `data/merchants/{merchant_id}/vector_store/`
- Query result filtering: MUST ensure results from merchant_a never leak into merchant_b conversations

1.3 Description of the research methodology
为了达成 1.2 节所述的研究目标，本研究采用了一种集成的“设计与开发”导向方法论，将大语言模型（LLM）的推理能力与检索增强生成（RAG）技术深度结合。该方法论由以下四个支柱构成：

1.3.1 模块化 Agent 架构
本研究的核心是从“单体式”聊天机器人转向基于模块化 Agent 的工作流。AI 的行为由结构化的状态机逻辑管理。该方法论通过将客服流程分解为意图解析、知识路由、不确定性评估和实证生成等离散且可观察的阶段，确保了系统的可控性。

1.3.2 语义意图驱动的检索理论
本研究提出了一种自适应知识路由方法。与在单一数据库中搜索的传统 RAG 不同，我们的方法论包括：

分层数据建模：将电商知识划分为结构化（产品目录）和非结构化（政策文档）层级。

意图-知识映射：利用语义解析确保检索引擎仅访问相关的知识库，从而最大限度地减少语义干扰和噪声。

1.3.3 不确定性感知与防护机制
本研究的一个关键理论组成部分是不确定性守门员。我们建立了一套量化 RAG 系统“置信度”的方法。通过引入基于阈值的决策逻辑，系统可以区分“检索到的知识是否充足”与“用户咨询是否存在歧义”，从而允许 Agent 主动触发澄清流程，而非生成幻觉内容。

1.3.4 多租户隔离与可扩展性设计
从系统工程的角度来看，该方法论强调商家隔离。我们采用物理隔离的数据架构，将每个商家的知识存储在独立的向量集合中。这不仅确保了数据安全，还使框架能够在不同的电商类别（如从学术书籍到大众小说）之间进行迁移验证。

1.3.5 评估与验证框架
为了科学地验证框架的有效性，本研究采用了对比实验设计：

基准对比：将提出的 Agent-RAG 系统与纯 LLM 模型和传统 RAG 模型进行对比。

基于指标的评估：使用准确率、检索精确度、幻觉率等定量指标，辅以用户满意度的定性分析。

【新增】1.3.6 实验评估层规范（Evaluation Layer Specification）

为了支撑论文的定量评估，`experiments/` 目录包含以下脚本标准：

**实验脚本目录结构**：
```
experiments/
├── test_cases_loader.py        # 从 data/evaluation_sets/test_cases_ground_truth.json 读取
├── run_llm_only.py             # Baseline: Pure LLM (no RAG)
├── run_vanilla_rag.py          # Baseline: Traditional RAG (single vector DB)
├── run_agent_rag.py            # Main: Intent-driven Agent-RAG
├── evaluation_metrics.py        # Compute Accuracy, Faithfulness, Hallucination Rate
└── generate_report.py          # Export results to CSV for paper figures
```

**Ground Truth Data Format** (`data/evaluation_sets/test_cases_ground_truth.json`):
```json
[
  {
    "id": 1,
    "question": "本店是否有《三体》？",
    "merchant": "merchant_a",
    "expected_answer": "有，《三体》由刘慈欣著，库存 15 册。",
    "source_documents": ["products/books_catalog.csv:row_1"],
    "intent_label": "PRODUCT_INQUIRY",
    "difficulty": "easy"
  }
]
```

**Output Metrics**:
- Accuracy: Exact/fuzzy match against `expected_answer`
- Faithfulness: Whether response only uses information from `source_documents`
- Hallucination Rate: Percentage of OOD (out-of-domain) queries answered with fabricated content
- Latency: Response time < 2 seconds

2.Literature Review
2.1 电商客服中 AI 的演进
早期的电商客服依赖于基于规则的系统 (Rule-based Systems)，这类系统基于“如果-那么”逻辑和预定义模板运行。虽然可靠，但难以处理人类语言的多样性。正如 Bawack 等人 (2022) 在其文献计量研究中指出的，AI 已将重点转向了个性化和信任构建。
大语言模型 (LLM)（如 GPT-4）的出现彻底改变了自然语言理解 (NLU) 领域。Meduri (2024) 强调，与僵化的模板相比，基于 LLM 的机器人具有更好的交互性。然而，一个显著的“研究空白”依然存在：大多数 LLM 部署是单体式（端到端）的。这产生了一种“黑盒”困境，即模型在给出答案时没有明确、可验证的推理路径。在电商等高精度行业，这种缺乏透明性的现象会导致不可控风险。例如，一个“黑盒”模型可能会为了维持对话流畅度或“讨好”用户，而优先选择生成自然但虚假的内容——比如仅仅为了顺应对话语境，就礼貌地确认一件根本不存在的商品是有货的。这种行为使得开发者难以诊断错误究竟源于知识检索的失败，还是模型内部逻辑的崩溃。
2.2 RAG (检索增强生成) 的理论基础
为了缓解 LLM 固有的“幻觉”问题（即模型因概率预测而非事实根据生成的虚假信息），检索增强生成 (RAG) 已成为行业标准。
核心机制：RAG 通过从外部知识库（向量数据库）检索相关的文档片段，并将其作为上下文“喂”给 LLM (Gao et al., 2023)。
领域应用：在电商领域，Guan 等人 (2024) 通过 BSharedRAG 框架证明，共享检索与生成的骨干网络可以显著提高准确率。
局限性：目前的 RAG 文献通常假设数据源是单一且统一的。在现实的多商家场景中，单体向量库会导致语义干扰（例如，将商家 A 的退货政策与商家 B 的混淆）。本研究识别出需要一种隔离式 RAG 架构来维护数据的完整性。
2.3 Agent 工作流与意图驱动逻辑
从“聊天机器人”向“AI Agent (智能体)”的转变代表了 AI 研究的最前沿。智能体的特点是能够使用工具并遵循结构化的工作流 (Wang et al., 2023)。
工作流编排：Yao 等人 (2024) 认为，将复杂任务分解为模块化步骤（意图解析 $\rightarrow$ 检索 $\rightarrow$ 生成）可以增强系统的透明度。
不确定性与健壮性：电商 AI 中一个关键但研究不足的领域是不确定性检测。大多数系统被设计为“总能给出答案”。然而，从学术角度看，“知道自己不知道”对于建立信任至关重要。本研究引入了 RAG 中的置信度阈值概念，确保系统在检索证据不足时触发澄清流程。
2.4 研究空白识别
通过对现有文献的综述，本研究识别出三个主要空白：
1.多品类 RAG 中的语义干扰：大多数 RAG 研究关注单一领域的准确性，但忽略了当一个系统服务于多个政策冲突的商家时，如何防止数据交叉污染。
2.缺乏不确定性把关机制：在电商 RAG 系统中，关于如何集成主动“澄清流”来处理歧义咨询的研究非常有限。
架构的可重用性：许多系统是针对特定领域“硬编码”的。一个允许商家数据“插件化”部署的模块化、工作流导向框架仍然是一个重大的工程与学术挑战。

【新增】**第 4 阶段 - 不确定性守门员与澄清流程 🔄 开发中（预计 4 月底完成）**
实现基于检索置信度的检测机制。若检索分数 C < 预设阈值 T，系统触发澄清流程而非生成幻觉内容。最后阶段受严格的"真实性"提示词约束，确保 LLM 仅使用检索片段并注明来源。【/新增】

3.2 数据基础设施与商家隔离
本阶段的一项重要进展是实现了多租户数据隔离策略。
递归数据摄取：开发了 DocumentParser 模块，利用 os.walk 自动扫描商家专用目录。

class DocumentParser:
    """支持 6 种文件格式的通用文档解析器"""
    
    def load_merchant_data(self, merchant_dir: str):
        """递归扫描商家目录，返回 [{'source': filename, 'content': text}]"""
        documents = []
        for root, dirs, files in os.walk(merchant_dir):  # 递归遍历
            for filename in files:
                ext = filename.split('.')[-1].lower()
                if ext == 'pdf':
                    content = self.parse_pdf(file_path)
                elif ext in ['csv', 'xlsx']:
                    # dtype=str 避免 NaN 导致的拼接异常
                    content = self.parse_excel_csv(file_path)
                # ... 支持 DOCX、TXT、MD
                if content:
                    documents.append({"source": filename, "content": content})
        return documents

def get_or_create_chroma(merchant_id: str, embeddings, persist_root=None):
    """确保每个商家拥有独立的向量集合，防止数据污染"""
    
    # 按商家创建独立持久化目录
    persist_directory = os.path.join(persist_root, merchant_id)
    
    # collection_name 使用 merchant_id 实现隔离
    chroma = Chroma(
        persist_directory=persist_directory,
        collection_name=merchant_id,  # 关键：商家隔离
        embedding_function=embeddings
    )
    return chroma

def ingest_merchant_documents(merchant_id, merchant_dir, embeddings=None):
    """解析 → 分片 → 向量化 → 隔离存储的完整流程"""
    
    # 1. 解析所有格式文件
    parser = DocumentParser()
    documents = parser.load_merchant_data(merchant_dir)
    
    # 2. 文本分片（保留元数据追溯）
    chunks = split_documents(documents, chunk_size=1000)
    
    # 3. 创建商家独立的向量库
    chroma = get_or_create_chroma(merchant_id, embeddings)
    
    # 4. 写入向量库
    texts = [c['text'] for c in chunks]
    metadatas = [c['metadata'] for c in chunks]
    chroma.add_texts(texts=texts, metadatas=metadatas)
    
    return {'status': 'ok', 'documents': len(documents), 'chunks': len(texts)}
